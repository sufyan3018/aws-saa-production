16>   VPC Notes
VPC actually zyada mushkil nahi hai — log isliye atakte hain kyunki saare pieces ek saath sikhaye jaate hain. Chalo ekdum scratch se, ek analogy ke saath.

VPC ko ek gated colony samjho.

Tumhara VPC = poori colony ki boundary (ek IP range, jaise 10.0.0.0/16 — matlab is colony mein itne "ghar" fit ho sakte hain).

Ab is colony ko tum subnets mein divide karte ho — colony ke andar alag-alag sections/blocks. Har subnet ek chhota IP range hota hai (jaise 10.0.1.0/24).

Do tarah ke subnets hote hain:

Public subnet — jiska raasta seedha bahar road (internet) tak jaata hai
Private subnet — jo colony ke andar hi rehta hai, bahar seedha nahi ja sakta

Ab teen cheezein jo isko control karti hain:

1. Internet Gateway (IGW) — colony ka main gate
Yeh poori colony ka ek hi gate hai jo internet se connect karta hai. Koi bhi subnet directly tabhi internet use kar sakta hai jab uska route table iss gate ki taraf point kare.

2. Route Table — "kaunse subnet se kaunsa raasta jaata hai"
Yeh basically ek signboard hai: "agar tumhe bahar jaana hai, IGW se jao" (public subnet mein) ya "sirf colony ke andar hi jaa sakte ho" (private subnet mein). Public subnet ka route table IGW ki taraf point karta hai — bas yahi ek cheez usko "public" banati hai, kuch aur nahi.

3. NAT Gateway — private ghar walon ke liye one-way exit
Agar private subnet mein koi cheez (jaise database server) ko sirf updates download karne hain internet se, par bahar se koi usse access na kar paaye — tab NAT Gateway use hota hai. Yeh public subnet mein baithta hai, aur private subnet ko "bahar jaane do, par bahar se andar aane mat do" wala one-way raasta deta hai.

4. Security Groups vs NACLs — do alag guards

Yeh sabse zyada confuse karta hai, isliye clearly:

	Security Group	NACL
Kahan lagta hai	Individual server (instance) ke darwaze pe	Poore subnet ki boundary pe
Kaise kaam karta hai	Sirf "allow" rules — jo nahi likha wo block	Allow aur Deny dono likh sakte ho
State	Stateful — agar andar aane diya, bahar jaane ka automatic allow	Stateless — dono directions explicitly allow karne padte hain

Analogy: Security Group = tumhare ghar ka darwaza guard (sirf tumhare ghar ke liye). NACL = colony ke us block ka gate guard (poore block ke liye, chahe andar kitne bhi ghar hon).

Ab bolo — inme se kaunsa part abhi bhi confusing lag raha hai? Route tables, NAT vs IGW, ya SG vs NACL? Usi pe zoom in karke ek practical scenario se samjhata hoon.|

AWS Systems Manager (SSM) is organized into four primary operational capability groups. Under these categories, AWS includes more than a dozen specialized sub-services and tools:

1. Node Management

These tools are used to connect to, configure, patch, and manage the underlying compute infrastructure (EC2 instances, on-premises virtual machines, and multi-cloud servers).
• Session Manager: Secure, one-click interactive shell and CLI access through a web browser, eliminating the need for SSH keys, open inbound ports, or bastion hosts.
• Run Command: Secure execution of scripts or shell commands at scale across vast server fleets simultaneously without direct login.
• Patch Manager: Automated vulnerability scanning and OS/software patch deployment based on customized patch baselines.
• State Manager: Automates configuration compliance to ensure managed nodes stay in a defined "desired state" (e.g., ensuring a specific security software agent is always running).
• Fleet Manager: A centralized user interface to view and manage the health, configuration, and operating systems of all servers in one place.
• Inventory: Automatically tracks software installations, operating system configurations, network settings, and application metadata on your nodes.
• Distributor: Simplifies building and securely distributing software packages (like monitoring tools, logs collectors, or security agents) to instances.
• Compliance: Aggregates and displays compliance statuses based on patch evaluations and State Manager rules.

2. Application Management

These tools manage application-level environments, variable parameters, and configuration secrets.
• Parameter Store: Centralized, secure storage for configuration strings, license codes, and encrypted secrets (such as database passwords), integrated with AWS KMS.
• AppConfig: Helps deploy application configurations and safe, dynamic feature flags independently of code deployments, featuring automatic validation and instant rollbacks.
• Application Manager: Aggregates operational status, resources, and problems contextually by application (e.g., grouped by an EKS cluster or CloudFormation stack).

3. Change Management

These services allow teams to safely introduce, schedule, and approve manual or automated updates to infrastructure.
• Automation: Executes multi-step operational runbooks (YAML/JSON templates) for routine infrastructure maintenance tasks, such as generating automated machine images (AMIs).
• Change Manager: An enterprise change-management workflow tool to request, review, approve, and track operational changes before execution.
• Maintenance Windows: Defines scheduled blocks of time for disruptive operations (like patching or system reboots) to prevent business downtime.
• Change Calendar: Establishes specific dates and times where infrastructure shifts are allowed or blocked (e.g., enforcing an operational freeze during major sales events).

4. Operations Management

A unified "single pane of glass" to look at overall health, aggregate issues, and track active cloud incidents.
• OpsCenter: Centralizes operational work items (called OpsItems), allowing DevOps engineers to view, track, and fix issues across various AWS services.
• Incident Manager: Coordinates automated incident response steps, alerts on-call teams, manages response chat rooms, and maps out post-incident analyses.
• Explorer: A highly customizable Operations dashboard that aggregates metrics, compliance state, and operational health reports across multiple accounts and regions.
